# 1. Главный принцип

MergeVue нельзя проектировать как набор экранов, где каждый экран самостоятельно решает, что «готово», что «ошибка», а что «доступно».

В системе одновременно существуют:

- состояние сделки;
- состояние исследования;
- состояние доказательств;
- состояние качества данных;
- состояние платного доступа;
- состояние корпоративного согласования;
- состояние респондента;
- состояние 42Q;
- состояние прогноза;
- состояние отчёта;
- состояние последующей проверки;
- права конкретного пользователя.

Поэтому:

> **состояние интерфейса является результатом нескольких независимых состояний, а не одной глобальной метки.**

# 2. Что уже существует в ядре

Текущая программная логика содержит реальные машинные состояния, которые необходимо сохранять как существующие контракты.

## 2.1. Проверка доказательства

Текущие значения:

- `unreviewed` → `Unreviewed`;
- `under_review` → `Under review`;
- `verified` → `Verified`;
- `disputed` → `Disputed`.

## 2.2. Уровень уверенности доказательства

Текущие значения:

- `high` → `High`;
- `medium` → `Medium`;
- `low` → `Low`;
- `cannot_determine` → `Cannot determine`.

`Cannot determine` является самостоятельным состоянием и не равно `Low`.

## 2.3. Отношение доказательства к выводу

Текущие значения:

- `supports` → `Supports`;
- `contradicts` → `Contradicts`;
- `context` → `Context`;
- `follow_up` → `Requires follow-up`.

# 3. Уже существующая fail-closed логика

В текущем ядре уже существуют состояния, при которых вычисленный анализ нельзя выпускать клиенту.

В частности используются:

- `paid_output_conditional`;
- `analyst_review_required`;

Следовательно:

> **«анализ вычислен» не означает «результат разрешён к выпуску».**

Дизайн обязан отображать эту границу.

---

# 4. Составное состояние страницы

Любая защищённая страница сделки определяется минимум следующими осями:

```text
AUTHENTICATION
+
DEAL LIFECYCLE
+
ENTITLEMENT
+
PERMISSION
+
DATA AVAILABILITY
+
ANALYSIS STATE
+
QUALITY GATE
+
OBJECT-SPECIFIC STATE
```

Например, пользователь может одновременно:

- быть авторизован;
- иметь доступ к сделке;
- иметь оплаченный платный контур;
- видеть раздел руководителей;
- но не иметь персонального прогноза,

потому что 42Q ещё не завершён.

Это нормальное состояние.

---

# 5. Запрет универсального «процента готовности»

MergeVue не должен сводить сложное состояние сделки к:

> `82% complete`

если такого объективного знаменателя нет.

Состояние сделки должно объяснять текущую фазу, а состояния объектов — собственную готовность.

# 7. Состояние сделки не заменяет состояние дочерних объектов

Даже при `Paid analysis active`:

- часть доказательств может быть `Unreviewed`;
- один прогноз может быть `Blocked`;
- другой — `Locked`;
- один руководитель может завершить 42Q;
- другой может отказаться;
- отчёт может оставаться `Draft`.

Дочерние объекты не наследуют статус сделки автоматически.

# 9. Limited и Blocked — разные состояния

## `Limited`

Система имеет право показать полезный, но ограниченный результат.

Пример UI-copy:

> `Analysis is available, but several material questions remain unresolved.`

## `Blocked`

Система не имеет права выпускать соответствующий вывод.

Пример:

> `A reliable conclusion cannot be issued until the conflicting evidence is resolved.`

`Blocked` нельзя визуально трактовать как просто «низкую уверенность».

# 11. Документ и доказательство — разные объекты

Один документ может быть `Processed`, но породить:

- три `Verified` доказательства;
- одно `Under review`;
- одно `Disputed`.

Поэтому:

> `Document processed` не означает `Evidence verified`.

# 19. Оплата не равна доступу

Формула:

> `ENTITLEMENT + PERMISSION = ACCESS`

Не:

> `PAYMENT = ACCESS`

Человек, который провёл оплату, не получает автоматически права читать чувствительные данные сделки.

# 24. Approved, Issued и Locked различаются

## `Approved`

Результат прошёл обязательные внутренние шлюзы и разрешён к выпуску.

## `Issued`

Клиентская версия фактически выпущена.

## `Locked`

Формулировка зафиксирована для будущей проверки и не может быть незаметно изменена.

Эти состояния нельзя объединять.

# 27. Missed и Falsified различаются

## `Missed`

Существенное фактическое событие произошло, но исходный прогноз его не охватил или не ожидал.

## `Falsified`

Заранее заданное условие опровержения выполнено и прогноз прямо не выдержал проверку.

---

# 28. Not determinable не является промахом

Используется, когда:

- нет достаточных последующих данных;
- событие нельзя надёжно наблюдать;
- источник недоступен;
- проверка исхода не может быть корректно завершена.

Его нельзя автоматически считать ни подтверждением, ни промахом.

# 33. Глобальные состояния страницы

Каждая страница должна быть проверена минимум на следующие универсальные состояния:

1. `loading`;
2. `ready`;
3. `empty`;
4. `partial`;
5. `permission_denied`;
6. `not_found`;
7. `error`;
8. `stale`;
9. `blocked`.

Не каждая страница использует все девять, но дизайнер обязан проверить применимость каждого.

---

# 34. Loading

Клиентская строка должна называть объект.

Не:

> `Loading...`

Лучше:

> `Loading deal evidence...`

или:

> `Preparing your public analysis...`

Если процесс долгий, одного спиннера недостаточно.

---

# 35. Empty

Пустое состояние должно отвечать:

- почему здесь пока ничего нет;
- что появится позже;
- какое действие возможно.

Пример:

> `No locked forecasts yet.`  
> `A forecast will appear here after it passes release review and is locked for future verification.`

---

# 36. Partial

`Partial` используется, когда часть результата уже доступна.

Например:

- открытые доказательства готовы;
- закрытые документы ещё обрабатываются.

Не следует скрывать уже доступную ценность за общим экраном ожидания.

---

# 37. Permission denied

Нужно различать:

- пользователь не авторизован;
- пользователь не является участником сделки;
- пользователь участник сделки, но не имеет права на конкретный объект.

Человеку без права нельзя раскрывать существование чувствительного объекта больше, чем необходимо.

---

# 38. Stale

Некоторые результаты устаревают после появления новых доказательств.

Клиентская формулировка:

> `New evidence has been added. This analysis needs to be refreshed.`

Старая версия не должна исчезать молча.

---

# 39. Blocked

`Blocked` используется только при реальном запрете продолжения.

Рядом всегда указывается причина.

Пример:

> `Release blocked: material evidence remains disputed.`

Не использовать `Blocked` для обычного ожидания.

---

# 40. Семантика цвета состояний

## Нейтральные

- Draft;
- Unreviewed;
- Not started;
- Not due;
- Archived.

## Процесс

- In progress;
- Under review;
- Researching;
- Processing.

Используется синий или нейтральный процессуальный акцент.

## Положительно завершённые

- Verified;
- Approved;
- Payment received;
- Confirmed.

Допускается зелёный.

## Требуют внимания

- Follow-up required;
- Information requested;
- Verification due;
- Limited by evidence.

Используется жёлто-оранжевый.

## Блокирующие или отрицательные

- Disputed;
- Blocked;
- Rejected;
- Falsified.

Красный применяется только когда смысл действительно блокирующий или отрицательный.

---

# 41. Красный не означает «плохая сделка»

Красный относится к состоянию конкретного объекта.

Он не должен превращать весь экран сделки в визуальное утверждение:

> `Bad Deal`.

MergeVue не выдаёт рекомендацию «покупать / не покупать».

---

# 42. Статус, риск и уверенность — разные оси

Одно доказательство может одновременно иметь:

```text
Review status: Verified
Confidence: Medium
Relationship: Supports
```

Это нормальное состояние.

Нельзя объединять:

- `Verified`;
- `High`;
- `Supports`

в одну зелёную метку «Good».

---

# 43. Состояние и доступ — разные оси

Объект может быть `Ready`, но пользователь не имеет права его видеть.

Сначала проверяется право.

Только затем отображается объектное состояние.

---

# 44. Состояние и коммерческий уровень — разные оси

42Q может быть куплен, но оставаться:

> `Invitation pending`.

Покупка не переводит аналитический объект автоматически в `Ready`.

---

# 45. Приоритет проверки видимости защищённой страницы

При открытии защищённого объекта система проверяет:

1. существует ли объект;
2. авторизован ли пользователь;
3. имеет ли он членство;
4. имеет ли право на тип объекта;
5. активирована ли соответствующая возможность;
6. существуют ли достаточные данные;
7. каков текущий статус объекта.

Такой порядок уменьшает риск утечки информации.

---

# 46. Fail-closed по правам и качеству

Если система не может надёжно определить:

- право;
- состояние обязательного шлюза;
- допустимость выпуска;
- наличие индивидуальных данных,

она выбирает ограничивающее состояние.

Не предполагать доступ или готовность.

---

# 47. Нельзя обходить блокировку навигацией

Если анализ заблокирован, интерфейс не должен автоматически вести пользователя к экрану финального результата.

Нужно показать:

- что остановлено;
- почему;
- что уже доступно;
- что требуется для разрешения.

---

# 48. Жизненный цикл обзора сделки

Одна и та же страница `Overview` меняет главный акцент.

## До результата

`Public analysis in progress`

## После результата

`Public analysis ready`

## При сборе данных

`Evidence collection`

## При платном анализе

`Paid analysis active`

## После выпуска

Главный материальный вывод и активные прогнозы.

## После закрытия

`Post-close monitoring`

Не нужно создавать новый маршрут для каждой фазы.

---

# 49. Жизненный цикл раздела Evidence

Раздел должен поддерживать:

- нет доказательств;
- есть непроверенные;
- идёт проверка;
- есть подтверждённые;
- есть спорные;
- есть блокирующее противоречие;
- появились новые данные после выпуска отчёта.

---

# 50. Жизненный цикл раздела Leaders

Раздел может быть:

- скрыт;
- доступен для подключения;
- активирован;
- без выбранных руководителей;
- с приглашёнными;
- с 42Q в процессе;
- с готовыми персональными прогнозами;
- с частично недоступными прогнозами.

Нельзя считать весь раздел одним состоянием.

---

# 51. Локальные группы Forecasts

Рекомендуемые пользовательские группы:

- `Working forecasts`;
- `Locked forecasts`;
- `Due for verification`;
- `Verified outcomes`.

Это может стать локальной навигацией раздела.

---

# 52. Отчёт и версия

Пользователь может видеть:

> `Report in quality review`

после выпуска:

> `Issued Apr 12, 2026`

при новой версии:

> `Superseded by version 1.3`

Старая версия остаётся доступной при наличии права.

---

# 53. Долгие фоновые процессы

Для:

- публичного исследования;
- обработки документов;
- анализа 42Q;
- многоступенчатой проверки

показывается реальная стадия, а не декоративный процент.

Допустимо:

> `Researching public sources`  
> `3 of 5 stages complete`

Недопустимо:

> `73%`

если 73 процента не имеют объективного вычислимого смысла.

---

# 54. Когда процент допустим

Только при объективном конечном наборе.

Например:

- `31 of 42 questions completed`;
- `8 of 10 files processed`.

Не использовать процент для «готовности анализа» без определённого знаменателя.

---

# 55. Что видит участник 42Q

Участнику достаточно состояний:

- `Invitation`;
- `Consent`;
- `In progress`;
- `Additional clarification`;
- `Completed`;
- `Expired`;
- `Revoked`.

Он не видит:

- `Forecast review`;
- `Forecast ready`;
- внутренние аналитические состояния.

---

# 56. Конечный экран 42Q

Допустимый английский текст:

> `Thank you. Your responses have been submitted.`

Запрещено:

> `Your profile is ready.`

> `Your personality type has been identified.`

---

# 57. Исторический кейс

Контентная последовательность:

- `Pre-event evidence`;
- `Forecast`;
- `Outcome hidden`;
- `Outcome revealed`;
- `Verification result`.

Это может быть не машинная state machine, но визуальная граница обязательна.

---

# 58. Версия методологии

В выпущенных и зафиксированных объектах сохраняется версия методологии.

Она должна быть доступна в:

- аудиторском блоке;
- отчёте;
- зафиксированном прогнозе.

---

# 59. Изменение методологии не переписывает прошлое

Старый зафиксированный прогноз не пересчитывается молча новой версией.

Новая модель может создать новую аналитическую версию.

Исходная зафиксированная версия сохраняется.

---

# 60. Машинный идентификатор и UI-copy разделены

Пример:

```text
machine: paid_output_blocked
UI: Blocked pending resolution
```

Машинные идентификаторы должны быть стабильны.

Английская клиентская формулировка может улучшаться без миграции данных.

---

# 61. Централизация клиентских строк

Даже при одной английской локали клиентские строки должны быть централизованы.

Причины:

- единообразие;
- контроль терминологии;
- отсутствие случайных русских строк;
- удобство редакторской проверки;
- будущая локализация.

Первая версия не обязана иметь тяжёлую мультиязычную инфраструктуру.

---

# 62. Автоматическая защита от русского интерфейса

Для первой версии рекомендуется автоматическая проверка:

> производственные системные строки клиентского интерфейса не содержат кириллицу.

Допустимые исключения:

- пользовательские данные;
- оригинальные названия компаний;
- оригинальные названия документов;
- внешние источники, содержащие кириллицу.

Системный интерфейс — только английский.

---

# 63. Американский английский

Предпочтительно:

- `analyze`, не `analyse`;
- `organization`, не `organisation`;
- `behavior`, не `behaviour`;
- `program`, не `programme`.

---

# 64. Логика не зависит от текста или цвета

Нельзя определять состояние по:

- тексту кнопки;
- цвету карточки;
- наличию иконки.

Источник истины — машинное состояние.

Текст и цвет только представляют его.

---

# 65. Каждое состояние обязано иметь контракт

Для каждого состояния необходимо определить:

- что оно означает;
- условие входа;
- разрешённые действия;
- запрещённые действия;
- возможные переходы;
- клиентскую английскую формулировку.

Если два состояния невозможно смыслово различить, их не следует создавать отдельно.

---

# 66. Важные переходы журналируются

Переходы:

- `Approved → Issued`;
- `Issued → Locked`;
- `Locked → verification outcome`

должны сохраняться в истории.

Нельзя перезаписывать существенный статус без аудиторского следа.

---

# 67. Что обязательно версионируется

Версионность обязательна для:

- отчётов;
- выпущенных прогнозов;
- зафиксированных прогнозов;
- существенных аналитических выводов после появления новых доказательств.

---

# 68. Что нельзя удалять из истории

Не должны исчезать:

- `Disputed`;
- `Blocked`;
- `Falsified`;
- `Missed`;
- `Superseded` report;
- `Revoked` access;
- проваленный шлюз выпуска.

Они могут перестать быть текущими, но остаются в аудиторском следе.

---

# 69. Уведомления о переходах

Уведомлять, когда:

- требуется действие пользователя;
- результат готов;
- доступ изменён;
- платёж требует действия;
- 42Q требует участия;
- наступила проверка прогноза;
- выпуск заблокирован по существенной причине.

Не уведомлять о каждом внутреннем техническом переходе.

---

# 70. Отчёт и приложение используют одни состояния

Если в приложении прогноз `Locked`, отчёт не может называть его `Draft`.

Если доказательство `Disputed`, экспорт не должен показывать его как `Verified`.

Отчёт — представление тех же объектов.

---

# 71. Экспертный интерфейс

Эксперт может видеть дополнительные внутренние поля:

- tier;
- route;
- gate;
- confidence cap;
- причины блокировки;
- список триггеров.

Клиент видит безопасную интерпретацию тех же состояний.

Это не две разные истины.

---

# 72. Пример составного состояния

```text
Deal lifecycle: Paid analysis active
Payment: Payment received
Evidence: 14 Verified / 2 Disputed
Quality gate: Senior review required
42Q / CEO: 42Q completed
CEO forecast: Quality review
Organizational forecast: Locked
Report: Draft
Verification: Not due
```

Это нормальное состояние.

Нельзя заменять его одним `82% complete`.

---

# 73. Пример блокировки после оплаты

```text
Deal lifecycle: Analysis in progress
Evidence: Material conflict detected
Quality gate: Blocked pending resolution
Organizational forecast: Blocked
Report: Blocked
Payment: Payment received
```

Клиент оплатил анализ, но результат пока нельзя выпустить.

Система должна показать это честно.

---

# 74. Пример индивидуального анализа

```text
42Q / CFO: 42Q completed
Individual analysis: Analysis in progress
Forecast: Not available
```

Промежуточный внутренний тип не показывается.

---

# 75. Пример после закрытия сделки

```text
Organizational forecast: Locked
Verification: Verification due
Outcome evidence: Evidence collection
Verification result: Not assigned
```

Это рабочая фаза продукта, а не просто архив отчёта.

---

# 76. Обязательные состояния для каждого макета

Для каждого существенного объекта дизайнер проверяет минимум:

- нормальное состояние;
- загрузку;
- пустое состояние;
- процесс;
- ограниченные данные;
- ошибку;
- блокировку;
- отсутствие права;
- завершённое состояние;
- устаревшее состояние, если применимо.

Макет только «идеального happy path» считается неполным.

# 77. Что разработчик должен получать из макета

Для каждого состояния должны быть понятны:

- машинный идентификатор;

# 80. Зафиксированные правила

1. Первая коммерческая версия продукта — только на английском языке для рынка США.
2. Русскоязычная документация не означает русскоязычный интерфейс.
3. Состояние продукта является составным.
4. Сделка не имеет одного универсального процента готовности.
5. Существующие состояния доказательств сохраняются.
6. `Cannot determine` не равно `Low`.
7. `Disputed` не равно технической ошибке.
8. Обработка документа и проверка доказательства — разные процессы.
9. Завершение опроса не означает подтверждение анализа.
10. Оплата не означает право доступа.
11. Оплата не означает готовность результата.
12. 42Q и персональный прогноз имеют отдельные состояния.
13. `42Q completed` не означает `Individual forecast ready`.
14. `Approved`, `Issued` и `Locked` различаются.
15. Результаты проверки прогноза: `Confirmed`, `Partially confirmed`, `Not determinable`, `Missed`, `Falsified`.
16. Существенные блокировки работают fail-closed.
17. Блокирующие и неудачные состояния сохраняются в истории.
18. Машинное состояние отделено от клиентской строки.
19. Клиентские строки централизованы.
20. Системные строки первой версии не содержат русского языка.

Документ считается достаточным, если дизайнер и разработчик могут без дополнительного продуктового решения:

- определить состояние организационного прогноза;
- определить состояние отчёта;
