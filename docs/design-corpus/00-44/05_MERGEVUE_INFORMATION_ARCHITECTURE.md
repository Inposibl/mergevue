# 1. Основной принцип информационной архитектуры

MergeVue состоит не из одного сайта, а из нескольких связанных информационных пространств.

Нельзя использовать одну и ту же навигацию для:

- человека, который впервые изучает продукт;
- пользователя, который анализирует конкретную сделку;
- приглашённого респондента;
- участника 42Q;
- члена инвестиционного комитета, читающего утверждённый отчёт;
- внутреннего проверяющего.

Целевая архитектура включает пять внешних оболочек и один внутренний контур.

## Оболочка 1. Публичный сайт

Объясняет продукт, метод, исторические доказательства и платные возможности.

## Оболочка 2. Анонимный анализ сделки

Проводит пользователя от ввода компаний до результата по открытым данным.

## Оболочка 3. Рабочее пространство сделки

Является основной профессиональной средой зарегистрированного пользователя.

## Оболочка 4. Пространство участника

Используется респондентами и участниками 42Q.

## Оболочка 5. Защищённое представление результата

Используется для чтения утверждённого отчёта лицами, которым не требуется полное рабочее пространство.

## Внутренний контур

Используется для проверок, исключений и контроля качества.

# 2. Что является главным объектом навигации

После регистрации главным объектом навигации является **сделка**.

Не анкета.

Не отчёт.

Не пользователь.

Не «диагностика».

Основная логика приложения:

> организация пользователя  
> → список сделок  
> → конкретная сделка  
> → доказательства, анализ, прогнозы и проверка внутри этой сделки

Это решение является зафиксированным.

---

# 3. Профессиональное основание архитектуры

Для сложных профессиональных продуктов с большим количеством функций рекомендуется:

- отделять публичную навигацию от рабочей;
- строить рабочую навигацию вокруг основного рабочего объекта;
- использовать боковую навигацию для глубоких рабочих структур;
- оставлять верхнюю панель для универсальных действий;
- постепенно раскрывать сложные функции;
- не показывать каждому пользователю все возможные разделы;
- использовать единые навигационные компоненты вместо уникальной навигации на каждой странице.

Для MergeVue основной рабочий объект — сделка, поэтому рабочее пространство должно быть сделко-центричным.

# 4. Текущее состояние маршрутов в `main`

На момент подготовки документа публичное приложение содержит следующие верхнеуровневые направления:

- главная;
- методология;
- девять сред взаимодействия;
- кейсы;
- старт диагностики.

Текущая боковая навигация в коде ведёт именно в эти пять разделов.

Текущий маршрут диагностики затем разворачивается в длинную линейную последовательность:

- подготовка;
- контекст сделки;
- уточнение качества доказательств;
- данные сделки;
- временная привязка;
- модуль покупателя;
- подтверждение покупателя;
- настройка наблюдения целевой компании;
- наблюдение целевой компании;
- диагностические уровни целевой компании;
- самооценка;
- цифровые приглашения;
- раскрытие результата;
- платное предложение;
- сбор электронной почты;
- запрос консультации.

Эта последовательность является ценной предметной работой, но не должна оставаться главным входом в новую архитектуру.

# 5. Главная структурная миграция

Текущая модель:

> главная → «начать диагностику» → анкеты → результат → платное предложение

Целевая модель:

> главная → анализ сделки по открытым данным → полезный результат → регистрация → собственные доказательства и опросы → платный анализ

Следствие:

> существующие анкеты не удаляются; они переходят из главного публичного пути в слой зарегистрированного углубления анализа.

Главная не должна пытаться вместить весь продукт.

Её задача:

1. сформулировать дорогую проблему;
2. объяснить, что делает MergeVue;
3. дать быстрый вход в анализ сделки;
4. показать три доказательства серьёзности:
   - метод;
   - девять сред;
   - исторические кейсы;
5. показать, что углубление возможно без превращения продукта в консалтинг.

Главная не является каталогом всех функций.

# 14. Исторические кейсы

Канонический индекс:

`/historical-replays`

Карточка кейса:

`/historical-replays/:caseId`

Текущая кодовая база содержит отдельные публичные кейсы старого формата.

Новая архитектура не должна привязываться к фиксированному числу кейсов.

Один шаблон должен поддерживать весь утверждённый корпус по мере готовности.

Внутри кейса необходимо поддержать последовательность:

1. контекст;
2. доступные до временной отсечки данные;
3. структурный анализ;
4. прогноз;
5. явная временная отсечка;
6. добровольное раскрытие фактического исхода;
7. сопоставление прогноза с исходом.

Фактический исход не должен автоматически занимать верх страницы.

# 15. Анонимный анализ сделки как отдельная оболочка

Анонимный анализ не должен использовать полную публичную навигацию.

Причина: пользователь уже выполняет задачу.

Рекомендуемая оболочка:

- логотип;
- название текущего шага;
- краткая ссылка «Как работает метод»;
- возможность выйти на главную.

Не следует показывать большое маркетинговое меню на каждом шаге.

---

# 16. Маршруты анонимного анализа

| Этап | Рекомендуемый маршрут |
|---|---|
| Ввод компаний | `/analyze` |
| Подтверждение компаний | `/analyze/confirm` |
| Минимальный контекст | `/analyze/context` |
| Исследование | `/analyze/research` |
| Публичный результат | `/analysis/:analysisToken` |

`analysisToken` должен быть непредсказуемым техническим идентификатором.

В адресе нельзя размещать:

- электронную почту;
- имя руководителя;
- типологическую информацию;
- закрытые данные;
- полный текст тезиса сделки.

---

# 17. Публичный результат

Публичный результат является самостоятельной страницей.

Он должен поддерживать:

- прямое возвращение по безопасной ссылке в рамках установленного срока;
- регистрацию без потери анализа;
- переход к историческим и методологическим объяснениям;
- раскрытие источников;
- предложение добавить собственные данные.

Главное действие:

> сохранить и дополнить анализ.

---

# 18. Учётная запись

Рекомендуемые маршруты:

| Действие | Маршрут |

# 19. Главная рабочая оболочка

После входа используется:

- постоянная боковая навигация;
- верхняя служебная панель;
- центральная область содержимого.

Верхняя панель предназначена для универсальных функций:

- переключение организации;
- переключение сделки;
- уведомления;
- справка;
- профиль.

Боковая навигация предназначена для разделов текущей сделки.

---

# 20. Главная страница рабочего пространства

`/workspace`

Не следует превращать эту страницу в аналитическую панель по всем сделкам, пока продукт не требует портфельного режима.

# 27. Почему риски находятся внутри анализа

Риск не является отдельным первичным объектом навигации.

Он является результатом:

> доказательства → структурная интерпретация → механизм → риск

Поэтому верхнеуровневая навигация «Риски» отдельно от «Анализа» создаст искусственное разделение одного процесса.

Внутри страницы риска можно делать глубокие ссылки на конкретный риск.

# 37. Почему не используется слово «повышение тарифа» в интерфейсе

Платный продукт MergeVue не должен выглядеть как обычная подписка на программное обеспечение.

Правильная рамка:

- объём проверки;
- экономическая значимость;
- закрытые доказательства;
- уровень контроля качества.

Поэтому в пользовательских текстах предпочтительно:

> «углубить анализ»  
> «заказать проверку»  
> «определить объём анализа»

а не:

> «повысить тариф».

# 45. Правила показа платных разделов

Следует различать три состояния.

## Релевантно, но не активировано

В контексте результата показывается объяснение возможности углубления.

## Активировано

Раздел появляется в навигации сделки.

Это уменьшает визуальный шум.

# 55. Почему старые номера экранов должны исчезнуть из пользовательской архитектуры

Названия вроде:

- «экран 6А»;
- «шаг 2-Б»;
- «уровень 1»;
- «экран 10Б»

являются внутренними историческими идентификаторами реализации.

Они не отражают пользовательскую задачу.

Пользователь должен видеть:

- «Опрос покупателя»;
- «Наблюдение целевой компании»;
- «Самооценка целевой компании»;
- «Противоречия»;
- «Текущий анализ».

Внутренние номера могут сохраняться в коде до завершения миграции, но не должны определять новую архитектуру.

# 56. Сохранение ценного текущего содержимого

Новая архитектура обязана сохранить и правильно разместить:

- главную идею прогноза поведения после сделки;
- существующий методологический материал;
- девять сред;
- страницы отдельных сред;
- ресурсную модель;
- высокий показатель совместимости как потенциально скрытый риск;
- доказательства и их качество;
- противоречия;
- текущие структурные прогнозы;
- исторические кейсы;
- публичный краткий отчёт;
- итоговый платный отчёт;
- аналитические ограничения.

Редизайн не означает переписывание продукта с нуля.

# 57. Существующая структура публичного отчёта как источник для приложения

Текущий публичный отчёт уже содержит ценные смысловые блоки:

- краткое решение;
- точки наблюдения;
- показатель совместимости и сценарий сделки;
- определённые среды;
- тезис столкновения;
- карта ресурсного конфликта;
- временная шкала ожидаемого напряжения;
- экономический перевод риска;
- рекомендуемые действия;
- пробел решения;
- что добавляет полный анализ;
- аудиторская информация.

Новая информационная архитектура должна распределить эти блоки по соответствующим разделам рабочего пространства, а не дублировать их как отдельный параллельный продукт.

# 60. Правила перенаправления после входа

Если пользователь:

- пришёл на защищённую страницу сделки — вернуть его туда после входа;
- пришёл из публичного результата — после регистрации создать или связать сделку и открыть её обзор;
- пришёл по приглашению респондента — не отправлять его на общее рабочее пространство;
- пришёл по приглашению 42Q — вернуть в поток 42Q;
- пришёл по защищённой ссылке на отчёт — сохранить режим чтения отчёта.

Контекст не должен теряться из-за авторизации.

---

# 61. Правила пустых состояний

Пустая страница должна объяснять не отсутствие данных, а следующий шаг.

Пример:

не:

> «Нет прогнозов».

а:

> «Прогноз появится после того, как система получит достаточную доказательную базу. Сейчас не разрешены следующие вопросы…»

Не:

> «Нет руководителей».

а:

> «Добавляйте руководителя только если его роль существенно влияет на тезис сделки».

---

# 62. Правила архивных сделок

Архивная сделка остаётся доступной для:

- чтения;
- отчётов;
- проверки прогнозов;
- истории.

Редактирование исходных зафиксированных прогнозов недоступно.

Архив не должен смешиваться с активными сделками по умолчанию.

---

# 63. Что не включается в первую информационную архитектуру

Пока не требуется отдельное верхнеуровневое пространство для:

- портфельной аналитики нескольких сделок;
- управления интеграционным офисом;
- кадровой системы;
- управления задачами;
- полного управления проектом интеграции;
- социальной сети респондентов;
- библиотеки всех документов организации вне сделок.

Добавление таких пространств потребует отдельного продуктового решения.

# 66. Критерий качества информационной архитектуры

Архитектура считается хорошей, если новый пользователь может ответить:

> «Где понять продукт?»

> «Где изучить метод?»

> «Где посмотреть доказательства на прошлых сделках?»

> «Где попробовать на своей сделке?»

А зарегистрированный пользователь:

> «Где мои сделки?»

> «Где доказательства?»

> «Где текущий анализ?»

> «Где прогноз?»

> «Где индивидуальный анализ руководителей?»

> «Где отчёт?»

> «Где проверить, сбылся ли прогноз?»

Без необходимости помнить номера шагов, внутренние коды или структуру методологии.

---

# 67. Критерий готовности документа

Документ считается достаточным для перехода к спецификациям глобальных правил и отдельных страниц, если дизайнер без дополнительных пояснений может:

- нарисовать полное дерево публичного сайта;
- нарисовать отдельную оболочку анонимного анализа;
- нарисовать структуру рабочего пространства сделки;
- показать все основные разделы сделки;
- определить, где находятся существующие опросы;
- показать платный контур;
- показать закрытые доказательства;
- показать место 42Q;
- показать персональный прогноз без типологического раздела;
- показать отчёты;
- показать последующую проверку;
- показать участнические потоки;
- показать центр доверия;
- объяснить, какие старые маршруты сохраняются, какие перенаправляются и какие перестают быть самостоятельными страницами;
- отличить клиентскую навигацию от внутренней;
- определить требования доступа к каждому пространству.

Если для любого крупного раздела остаётся вопрос «где это живёт?», информационная архитектура ещё не готова.

# 68. Трассируемость к текущему дереву проекта

При проектировании и последующей разработке необходимо сверяться минимум со следующими источниками текущего `main`:

- `src/flow/contradictionEngine.js` — предметная модель противоречий;
