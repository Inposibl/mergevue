**Область действия:** публичный сайт, анонимный анализ сделки, регистрация, рабочее пространство, организационные опросы, закрытые документы, корпоративное согласование, платный анализ, 42Q, отчёты, последующая проверка

# 0. Главный принцип

MergeVue не должен требовать доверия авансом.

Каждая следующая степень доверия должна быть заработана предыдущей степенью ценности.

Правильная последовательность:

> показать полезность  
> → объяснить основание  
> → показать ограничения  
> → попросить минимально необходимое действие  
> → создать дополнительную ценность  
> → только затем просить более чувствительные данные или деньги

Неправильная последовательность:

> регистрация  
> → длинная анкета  
> → закрытые данные  
> → оплата  
> → только потом первое доказательство полезности

---

# 1. Что означает постепенное раскрытие в MergeVue

Постепенное раскрытие применяется одновременно к четырём разным объектам:

1. сложности интерфейса;
2. глубине методологии;
3. чувствительности данных;
4. коммерческому обязательству пользователя.

Это разные оси.

Пользователь может хотеть:

- глубже читать методологию, но не создавать учётную запись;
- создать учётную запись, но не передавать закрытые документы;
- передать закрытые документы, но не запускать 42Q;
- заказать индивидуальный прогноз, но только по двум критическим руководителям;
- читать отчёт, но не иметь доступа к рабочему пространству.

Архитектура не должна связывать эти действия искусственно.

---

# 2. Профессиональное основание

Профессиональная практика проектирования сложных цифровых сервисов поддерживает следующие принципы.

## 2.1. Показывать сначала основное

На первом уровне интерфейса пользователь должен видеть только функции, необходимые для основной задачи.

Редкие, продвинутые или специализированные функции раскрываются позже.

## 2.2. Каждый вопрос должен иметь причину

До добавления любого вопроса команда должна знать:

- зачем нужна эта информация;
- как она будет использована;
- кому действительно нужно её предоставлять;
- как проверяется её качество;
- как она хранится и защищается.

## 2.3. Показывать только относящиеся к пользователю шаги

Если вопрос или функция не относятся к конкретному сценарию, их не следует показывать.

## 2.4. Сложный процесс следует делить на понятные этапы

Особенно это важно для:

- регистрации;
- корпоративного согласования;
- загрузки закрытых материалов;
- приглашений;
- 42Q.

## 2.5. Неизвестность должна быть допустимым ответом

Если пользователь действительно может не знать ответ, интерфейс обязан это позволять.

## 2.6. Приватность является отдельным риском продукта

Сбор данных должен оцениваться не только по полезности для анализа, но и по риску для человека и организации, чьи данные обрабатываются.

# 3. Лестница доверия

MergeVue использует семь уровней доверия.

## Уровень 0. Публичное чтение

Пользователь ничего не передаёт.

Он может:

- прочитать главную;
- изучить метод;
- изучить девять сред;
- посмотреть исторические кейсы;
- изучить ограничения;
- изучить безопасность и правила работы с данными.

## Уровень 1. Анонимный анализ

Пользователь передаёт минимальный контекст сделки:

- названия компаний;
- минимальный контекст сделки.

Взамен получает:

- исследование открытых источников;
- зоны риска;
- неизвестные;
- вопросы;
- временные гипотезы.

## Уровень 2. Учётная запись

Пользователь передаёт контактные данные, необходимые для сохранения работы.

Взамен получает:

- сохранённую сделку;
- историю;
- возможность вернуться;
- возможность добавить собственные сведения.

## Уровень 3. Внутренние наблюдения

Пользователь передаёт организационные сведения, не являющиеся закрытым документным корпусом.

Взамен получает:

- уточнение анализа;
- сравнение публичного и внутреннего взгляда;
- разрешение или усиление противоречий.

## Уровень 4. Закрытые материалы

Клиент передаёт закрытые документы и более чувствительные сведения.

Взамен получает:

- платную проверку;
- глубокий доказательный анализ;
- экономическую привязку;
- усиленную проверку качества.

## Уровень 5. Индивидуальные данные 42Q

Конкретный руководитель предоставляет персональные ответы.

Взамен заказчик получает:

- индивидуальный поведенческий прогноз без публикации внутреннего типа.

Участник 42Q не обязан получать клиентский результат.

## Уровень 6. Последующая проверка

Клиент предоставляет или подтверждает фактические события после закрытия сделки.

Взамен получает:

- проверку зафиксированных прогнозов;
- историю подтверждений, промахов и неопределённых исходов.

---

# 4. Правило обмена ценностью

Каждая ступень должна отвечать на вопрос:

> «Что пользователь получает немедленно за то, что сейчас предоставляет?»

Если ответ нельзя сформулировать ясно, переход преждевременен.

Примеры.

## Названия компаний

Пользователь получает публичный анализ.

## Регистрация

Пользователь получает сохранение и продолжение уже готового результата.

## Собственные наблюдения

Пользователь получает обновление гипотез.

## Закрытые документы

Пользователь получает более глубокую доказательную проверку.

## 42Q

Заказчик получает индивидуальный поведенческий прогноз, который без персональных данных система не имеет права строить.

---

# 5. Правило минимально необходимого запроса

MergeVue должен запрашивать минимальный объём данных, достаточный для следующего решения.

Нельзя просить данные «на будущее» только потому, что они могут когда-нибудь пригодиться.

Перед добавлением каждого поля необходимо ответить:

1. какое решение зависит от этого поля;
2. может ли система получить сведения сама;
3. можно ли задать вопрос позже;
4. нужен ли ответ всем пользователям;
5. является ли ответ чувствительным;
6. что произойдёт, если пользователь не знает ответа.

---

# 6. Протокол вопроса

Для каждого вопроса в продукте должен существовать внутренний протокол.

Минимальная структура:

| Поле протокола | Содержание |
|---|---|
| Вопрос | что спрашиваем |
| Причина | зачем это необходимо |
| Решение | какое решение меняется |
| Обязательность | обязательно или нет |
| Кому задаётся | роль пользователя |
| Источник | почему пользователь способен знать ответ |
| Чувствительность | уровень чувствительности |
| Проверка | как проверяется качество |
| Неизвестность | допустим ли ответ «не знаю» |
| Хранение | где и как хранится |
| Видимость | кто может видеть ответ |

Этот протокол создаётся до проектирования формы.

# 7. Уровни чувствительности данных

Для проектирования интерфейса вводятся пять уровней чувствительности.

## Уровень А. Публичные сведения

Например:

- название компании;
- публичная сделка;
- пресс-релиз;
- публичный руководитель;
- открытый источник.

## Уровень Б. Рабочие сведения пользователя

Например:

- заметка о сделке;
- субъективное наблюдение;
- приоритет проверки;
- внутренняя гипотеза пользователя.

## Уровень В. Закрытые корпоративные данные

Например:

- закрытый документ;
- внутренний финансовый материал;
- внутренний организационный документ;
- закрытый план интеграции.

## Уровень Г. Персональные чувствительные данные

Например:

- ответы 42Q;
- индивидуальный поведенческий материал;
- сведения, относящиеся к конкретному руководителю.

## Уровень Д. Производные чувствительные выводы

Например:

- персональный прогноз;
- внутренний аналитический вывод по руководителю;
- закрытая оценка экономической экспозиции;
- служебная типологическая переменная.

Чем выше уровень, тем строже:

- права;
- объяснение цели;
- журналирование;
- экспорт;
- удаление;
- человеческий доступ.

---

# 8. Что разрешено до регистрации

До регистрации разрешено:

- читать публичный сайт;
- читать методологию;
- изучать девять сред;
- изучать исторические кейсы;
- вводить компании;
- задавать минимальный контекст;
- получать результат по открытым данным.

До регистрации нельзя требовать:

- электронную почту только ради просмотра результата;
- полный профиль пользователя;
- номер телефона;
- название работодателя, если оно не нужно;
- внутренние документы;
- организационный опрос;
- 42Q.

---

# 9. Когда разрешена регистрация

Регистрация становится естественной после первой полученной ценности.

Правильный момент:

> публичный анализ уже готов, а пользователь хочет его сохранить или дополнить.

Интерфейс должен объяснить:

> «Создайте учётную запись, чтобы сохранить этот анализ и добавить сведения, которых нет в открытых источниках».

Регистрация не должна формулироваться как:

> «Зарегистрируйтесь, чтобы узнать результат».

---

# 10. Что разрешено после регистрации

После регистрации можно раскрыть:

- список сделок;
- рабочее пространство;
- собственные наблюдения;
- организационные опросы;
- приглашения респондентов;
- сравнение публичных и внутренних данных;
- историю изменений;
- возможность углубить анализ.

Но закрытые документы ещё не должны запрашиваться автоматически.

---

# 11. Когда разрешено просить организационные наблюдения

Организационное наблюдение разрешено просить, если:

- публичный анализ уже сформировал конкретную неизвестность;
- ответ пользователя способен изменить вывод;
- пользователь понимает, к какой части анализа относится вопрос.

Пример:

> «Открытые источники не позволяют определить, кто фактически принимает решение по продуктовой архитектуре. Что наблюдаете вы?»

Это лучше, чем:

> «Ответьте на 67 вопросов».

---

# 12. Как должны появляться 67 вопросов

Замороженная анкета является методологическим инструментом.

Она не должна определять информационную архитектуру.

Правильная роль:

- углублённый способ добавить структурированные наблюдения;
- доступен после публичного анализа;
- запускается тогда, когда пользователю понятна цель;
- может быть назначен соответствующему респонденту.

Интерфейс должен объяснять:

- зачем нужен модуль;
- какую часть неопределённости он закрывает;
- кто должен отвечать;
- сколько потребуется времени.

---

# 13. Неизвестность в формах

Если вопрос допускает отсутствие знания, пользователь должен иметь честный вариант:

- «не знаю»;
- «не наблюдал»;
- «недостаточно информации».

Нельзя заставлять пользователя выбирать ближайший ответ.

Это особенно важно, потому что в MergeVue:

> неизвестное не равно отрицательному сигналу.

---

# 14. Когда разрешено предлагать платный анализ

Платный анализ разрешено предлагать, если существует понятная причина.

Минимум одна из следующих:

- открытых данных недостаточно для материального вопроса;
- внутренние наблюдения выявили противоречие;
- требуется закрытый документ;
- существует существенная зависимость инвестиционного тезиса;
- требуется индивидуальный прогноз руководителя;
- требуется усиленная проверка;
- требуется зафиксированный профессиональный отчёт.

Нельзя показывать дорогой анализ только потому, что пользователь закончил бесплатный шаг.

---

# 15. Как раскрывается коммерческая сложность

Не нужно сразу показывать пользователю все уровни 5 000, 10 000, 15 000 и 30 000 долларов.

Правильная последовательность:

1. показать, что осталось нерешённым;
2. показать, почему это важно;
3. показать экономическую зависимость;
4. предложить соответствующий объём анализа;
5. дать возможность сравнить другие уровни при необходимости.

То есть:

> проблема → значение → объём проверки → цена

а не:

> таблица тарифов → выберите пакет.

---

# 16. Когда разрешено запрашивать экономическую информацию

Экономическая информация запрашивается только тогда, когда пользователь:

- рассматривает платный анализ;
- хочет связать организационный риск с тезисом сделки;
- имеет право раскрывать эту информацию.

Нельзя требовать:

- стоимость сделки;
- внутренний план синергий;
- финансовую модель

для получения базового публичного анализа.

---

# 17. Когда разрешено просить закрытые документы

Закрытые документы можно запрашивать только после четырёх условий.

## Условие 1. Пользователь понимает причину

Должно быть ясно, какой вопрос документы помогут проверить.

## Условие 2. Пользователь понимает режим обработки

До загрузки видны:

- правила доступа;
- хранение;
- удаление;
- человеческий доступ;
- использование внешних поставщиков.

## Условие 3. Пользователь подтверждает полномочие

Он должен подтвердить право предоставить материалы.

## Условие 4. Активирован соответствующий платный контур

Закрытые документы не являются бесплатным способом улучшения результата.

---

# 18. Неправильный запрос закрытых документов

Нельзя использовать формулировку:

> «Загрузите всё, что у вас есть».

Правильный запрос должен быть предметным:

> «Для проверки риска потери продуктовой автономии полезны: схема полномочий, интеграционный план и документы о будущей структуре принятия решений».

Это снижает объём ненужных данных и повышает качество анализа.

---

# 19. Раскрытие центра доверия перед загрузкой

До первой загрузки закрытого материала пользователь должен иметь быстрый доступ к:

- безопасности;
- конфиденциальности;
- правилам работы с данными;
- удалению;
- человеческому доступу;
- сведениям о поставщике.

Эти материалы нельзя скрывать только в правовой документации.

---

# 20. Когда разрешено раскрывать 42Q клиенту

42Q не должен постоянно рекламироваться всем пользователям.

Он раскрывается, когда одновременно выполняются условия:

1. существует конкретный руководитель;
2. его роль существенна для сделки;
3. клиент хочет прогноз поведения именно этого человека;
4. активирован платный индивидуальный анализ.

До этого 42Q остаётся методологической возможностью, а не главным элементом интерфейса.

---

# 21. Когда разрешено приглашать руководителя к 42Q

До отправки приглашения клиент должен указать:

- кого приглашает;
- роль;
- почему роль существенна;
- связь с зависимостью сделки.

Система должна подтвердить:

> индивидуальный прогноз требует персональных данных и не будет строиться по должности, публичному профилю или среде компании.

---

# 22. Что должен знать участник 42Q до начала

До первого вопроса участник должен понимать:

- кто пригласил;
- зачем проводится процедура;
- что собирается;
- сколько времени потребуется;
- как используются ответы;
- кто имеет доступ;
- получает ли он собственный результат;
- как обрабатываются его данные;
- куда обращаться по вопросам.

Не следует раскрывать:

- гипотезу заказчика;
- предполагаемый риск по человеку;
- внутреннюю типологическую модель;
- желаемый результат.

---

# 23. Согласие участника 42Q

Согласие должно быть отдельным действием.

Нельзя считать согласием:

- переход по ссылке;
- начало ответа;
- наличие корпоративного адреса;
- факт трудовых отношений.

Интерфейс должен фиксировать:

- дату;
- версию текста согласия;
- идентификатор приглашения.

Юридическая форма согласия будет определена отдельно с учётом применимого права.

---

# 24. Что клиент видит во время 42Q

Клиент может видеть только процессуальные состояния:

- приглашён;

Внутренняя типология остаётся скрытой.

# 31. Раскрытие экономической экспозиции

Второй уровень:

- основание оценки;

Третий уровень:

- расчётные допущения;

# 32. Раскрытие платных функций в навигации

Платная функция может находиться в трёх состояниях.

## Скрыта

Функция пока не относится к задаче пользователя.

## Объяснена контекстно

Пользователь столкнулся с ограничением, которое она решает.

## Активирована

После покупки функция становится полноценным разделом сделки.

Это правило распространяется на:

- закрытые доказательства;
- экономическую экспозицию;
- руководителей;
- 42Q;
- углублённый отчёт.

# 33. Запрет «кладбища заблокированных функций»

- замками;
- серыми платными разделами;
- рекламными плашками;
- постоянными предложениями купить.

Это создаёт ощущение искусственно урезанного продукта.

Платная возможность появляется там, где пользователь уже понимает её необходимость.

Покупка дорогого анализа требует доверия не только пользователя, но и организации.

# 35. Права доступа должны раскрываться по необходимости

Простой пользователь не должен сначала настраивать сложную матрицу прав.

Правильная последовательность:

Сложная настройка персональных данных и 42Q появляется только при соответствующем использовании.

# 36. Принцип ожидаемого доступа

Перед каждым приглашением система должна ясно показывать:

> «Этот человек сможет видеть…»

> «Этот человек не сможет видеть…»

- внешнего консультанта;
- респондента;

# 37. Постепенное раскрытие после закрытия сделки

До закрытия основной интерфейс отвечает:

После закрытия постепенно раскрываются:

- контрольные точки;
- фактические события;
- сопоставление с прогнозом;
- итоговый статус.

Раздел проверки не должен перегружать пользователя до того, как появляется первый зафиксированный прогноз.

# 38. Уведомления как форма постепенного возвращения

Система не должна просить пользователя регулярно проверять страницу.

- завершён опрос;
- завершён 42Q;
- появился конфликт;
- требуется дополнительный документ;
- наступило контрольное окно.

Каждое уведомление должно вести прямо к нужному действию.

# 39. Условия перехода между ступенями

| Переход | Условие |
|---|---|
| Публичный сайт → анализ | пользователь хочет проверить реальную сделку |
| Анализ → регистрация | публичный результат уже создан |

| Внутренние данные → платный анализ | существует материальный нерешённый вопрос |

| Прогноз → фиксация | пройдены обязательные проверки |
| Фиксация → последующая проверка | наступило соответствующее временное окно |

# 42. Что никогда не должно скрываться постепенным раскрытием

Постепенное раскрытие нельзя использовать, чтобы спрятать существенное ограничение.

Всегда видимыми должны быть:

- неизвестность, если она влияет на вывод;
- существенное противоречие;
- факт отсутствия 42Q при персональном прогнозе;
- факт использования закрытых данных;
- статус «прогноз» в отличие от «факт»;
- значимое ограничение;
- отсутствие достаточного основания;
- статус фиксации прогноза.

Дополнительные детали можно скрывать, сам факт — нельзя.

# 43. Принцип обратимости

Если пользователь повысил уровень доверия, это не означает, что действие необратимо.

Там, где возможно, он должен иметь возможность:

- удалить наблюдение;
- отозвать приглашение;
- удалить документ;
- изменить права;
- архивировать сделку;
- запросить удаление данных.

Ограничения обратимости должны быть объяснены заранее.

Зафиксированный прогноз является исключением:

> его исходная версия сохраняется как часть аудиторского следа.

---

# 44. Принцип отсутствия скрытого расширения цели

Данные, предоставленные для одной цели, не должны незаметно использоваться для другой клиентской цели.

Пример:

42Q собирается для прогноза поведения в контексте конкретной сделки.

Это не означает автоматического права использовать ответы для:

- кадровой аттестации;
- продвижения;
- увольнения;
- компенсации;
- общей оценки пригодности сотрудника.

---

# 45. Особое правило 42Q

Интерфейс и отчёт должны прямо поддерживать границу:

> MergeVue не принимает кадровое решение по человеку.

Индивидуальный прогноз относится к:

- рабочему поведению;
- изменению условий;
- интеграционному давлению;
- риску исполнения роли;
- риску для сделки.

Он не является самостоятельным решением о судьбе сотрудника.

---

# 46. Принцип раздельного доверия организации и человека

Клиентская организация может иметь право заказать анализ.

Это не означает, что конкретный человек автоматически дал согласие на индивидуальный сбор данных.

Поэтому:

- договор с клиентом;
- полномочия владельца сделки;
- согласие участника 42Q

являются разными сущностями.

---

# 47. Показатель успешности лестницы доверия

Не следует оптимизировать продукт только под максимальное количество переданных данных.

Хорошая лестница доверия означает:

- пользователь понимает причину каждого запроса;
- отказ не ломает уже созданную ценность;
- чувствительные данные появляются поздно;
- платный переход выглядит логичным;
- респонденты понимают границы участия;
- 42Q не воспринимается как скрытая оценка личности.

# 48. Аналитика пользовательского пути

- посещение → запуск анализа;

- регистрация → внутреннее наблюдение;
- наблюдение → обновлённый анализ;
- бесплатный анализ → платная квалификация;
- квалификация → корпоративное согласование;
- согласование → оплата;
- оплата → загрузка материалов;

- приглашение → согласие;
- согласие → завершение;
- прогноз → последующая проверка.

- незавершённые формы;
- вопросы о данных;
