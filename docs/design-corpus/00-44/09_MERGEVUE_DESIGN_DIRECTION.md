# 09. Визуальное направление MergeVue

**Статус документа:** подчинённая дизайнерская спецификация, производная от существующего визуального канона  
**Назначение:** перевести уже существующие визуальные правила MergeVue в единый русскоязычный ориентир для проектирования публичного сайта, рабочего пространства сделки, платного контура, 42Q и отчётов  
**Область действия:** публичный сайт, методологическая библиотека, исторические кейсы, анонимный анализ сделки, рабочее пространство, платный анализ, закрытые доказательства, индивидуальный прогноз, отчёты, последующая проверка  
**Версия:** 1.0  
**Дата:** 15 сентября 2026 года  
**Связанные документы:** `00_MERGEVUE_DESIGN_PROGRAM_OVERVIEW_v1.1.md`, `01_MERGEVUE_PRODUCT_NORTH_STAR.md`, `05_MERGEVUE_INFORMATION_ARCHITECTURE.md`, `06_MERGEVUE_TRUST_AND_PROGRESSIVE_DISCLOSURE.md`, `08_MERGEVUE_CONTENT_AND_CLAIMS_GOVERNANCE.md`

---

# 0. Граница полномочий этого документа

Этот документ **не создаёт новый визуальный канон с нуля**.

Он обязан следовать уже существующему правилу проекта:

> при создании новых экранов, отчётов и рабочих поверхностей сначала используется существующий принятый визуальный канон; новый шаблон создаётся только там, где существующий канон действительно не покрывает новую продуктовую задачу.

В управляющих правилах проекта отдельно закреплено:

> печатные и интерфейсные эталоны являются источником истины только для визуального языка и компоновки; они не являются источником методологических или числовых значений.

Следовательно:

- внешний вид может наследоваться из канона;
- числовой смысл всегда берётся из текущей методологии и программной логики;
- старый красивый макет не имеет права переопределять текущий показатель;
- новый дизайн не имеет права создавать параллельный визуальный язык MergeVue.

---

# 1. Состояние физического визуального канона в текущем дереве

`AGENTS.md` указывает принятый визуальный источник:

`docs/reference/print-canon/`

и принятые печатные и интерфейсные спецификации.

Однако в текущем `main` каталог `docs/reference/` физически содержит только:

- `root-definitional-e9-corr3`;
- `root-definitional-v1.7`.

Каталог `docs/reference/print-canon/` по указанному пути в текущем дереве отсутствует.

Это означает:

1. сам указатель полномочий сохраняется;
2. отсутствие каталога нельзя интерпретировать как отмену принятого визуального направления;
3. нельзя придумывать содержимое отсутствующего каталога;
4. фактически доступным механическим выражением канона является действующий канонический рендерер отчёта и связанные принятые правила;
5. если каталог будет восстановлен или обнаружен в другом связанном источнике, этот документ необходимо повторно сверить с ним.

# 2. Фактически доступный визуальный источник

Действующий файл:

`src/reporting/mergevueForecastBriefDesignRenderer.js`

использует специальный класс:

`mergevue-forecast-brief-canon`

и явный атрибут визуального контракта.

В истории проекта этот рендерер был перенесён из архивного канонического дизайна, после чего неоднократно уточнялись читаемость, компоновка, печатное представление и информационная плотность.

Для данного документа он является основным физически доступным визуальным ориентиром.

---

# 3. Главная визуальная идея

MergeVue должен восприниматься как:

> **профессиональная система инвестиционно-операционного анализа сделки, в которой каждый существенный вывод можно раскрыть до его основания.**

Визуально продукт должен находиться ближе к:

- профессиональному инвестиционному меморандуму;
- аналитическому рабочему пространству;
- качественному отчёту по комплексной проверке;
- системе доказательной поддержки решения,

чем к:

- кадровому тесту;
- сайту психологической типологии;
- обычной панели показателей программного обеспечения;
- биржевому терминалу;
- яркому сайту стартапа про искусственный интеллект;
- презентации консалтинговой компании;
- развлекательной визуализации «культуры».

---

# 4. Характер бренда

Базовые визуальные характеристики:

- сдержанный;
- точный;
- интеллектуальный;
- профессиональный;
- доказательный;
- спокойный;
- современный;
- плотный по содержанию, но не перегруженный;
- дорогой без демонстративной роскоши.

Продукт не должен выглядеть:

- тревожным;
- агрессивным;
- футуристическим ради футуризма;
- неоновым;
- игровым;
- психометрическим;
- «магическим искусственным интеллектом».

---

# 5. Главная визуальная иерархия

На любой аналитической странице иерархия должна читаться в следующем порядке:

1. что это за объект или решение;
2. какой главный вывод;
3. насколько он обоснован;
4. какой механизм стоит за выводом;
5. когда он должен проявиться;
6. что наблюдать;
7. какие данные его поддерживают;
8. какие существуют ограничения;
9. что делать дальше.

Дизайн не должен начинаться с графика только потому, что график визуально эффектен.

---

# 6. Базовая цветовая система существующего канона

Текущий канонический рендерер использует следующий фундамент.

| Назначение | Текущее каноническое значение |
|---|---|
| Основной фон | `#F6F7F8` |
| Основной текст | `#161616` |
| Вторичный текст | `#555D66` |
| Третичный текст | `#8A949E` |
| Основная поверхность | `#FFFFFF` |
| Вторичная поверхность | `#F3F5F7` |
| Разделительная линия | `#D9DDE2` |
| Усиленная линия | `#B9C1CA` |
| Основной акцент | `#2E75B6` |
| Мягкий акцентный фон | `#E8F2FB` |
| Положительный сигнальный цвет | `#2E7D32` |
| Промежуточный сигнальный цвет | `#E8A33D` |
| Рисковый сигнальный цвет | `#C0392B` |

Эта палитра является исходной для будущей дизайн-системы.

Дизайнер может предложить техническую нормализацию оттенков для цифровой доступности, но не должен заменять весь визуальный язык без отдельного решения.

---

# 7. Роль основного синего акцента

Синий используется для:

- ссылок;
- активного состояния;
- номера раздела;
- временной метки;
- ключевого технического идентификатора;
- выбранного элемента;
- основной кнопки;
- мягкого информационного выделения.

Синий **не означает «хороший результат»**.

---

# 8. Семантические цвета

Зелёный, жёлто-оранжевый и красный используются только там, где существует реальный семантический статус.

## Зелёный

Допустим для:

- подтверждённого состояния;
- выполненной проверки;
- успешно зафиксированного события.

## Жёлто-оранжевый

Допустим для:

- промежуточного состояния;
- необходимости наблюдения;
- частичного основания;
- ожидающей проверки.

## Красный

Допустим для:

- существенного риска;
- блокирующего противоречия;
- явного нарушения;
- невозможности выпуска.

Красный не должен становиться фоном всей страницы с риском.

---

# 9. Цвет не является единственным носителем смысла

Любой семантический цвет сопровождается:

- текстовым названием;
- формой или символом при необходимости;
- описанием состояния.

Пользователь не должен различать риск, подтверждение или неопределённость только по цвету.

---

# 10. Типографика

Действующий канон использует основной стек:

`Inter, Arial, sans-serif`

Для технического слоя используется моноширинный стек:

`ui-monospace, SFMono-Regular, Consolas, monospace`

Будущая система сохраняет эту двухуровневую логику.

## Основной шрифт

Используется для:

- заголовков;
- основного текста;
- выводов;
- объяснений;
- действий.

## Моноширинный шрифт

Используется для:

- временных меток;
- идентификаторов;
- номеров разделов;
- состояний;
- источников;
- версий;
- аудиторского следа;
- коротких технических подписей.

Моноширинный шрифт не используется для длинных абзацев.

---

# 11. Типографический характер

Канон использует:

- умеренно крупные заголовки;
- высокий контраст между главным значением и пояснением;
- небольшие технические подписи;
- верхний регистр только для коротких служебных обозначений;
- увеличенный межбуквенный интервал в служебных подписях;
- табличные цифры для сравнимых числовых данных.

Это следует сохранять.

---

# 12. Типографическая пропорция

В действующем отчёте присутствуют ориентиры:

- главный заголовок — около 44 пикселей;
- заголовок раздела — около 19 пикселей;
- важный аналитический тезис — около 20 пикселей;
- основной плотный отчётный текст — примерно 12,5–14 пикселей;
- технические подписи — примерно 9,5–11 пикселей.

Для веб-приложения это не обязательная пиксельная норма.

Обязательна **пропорция иерархии**.

В веб-приложении основной текст должен быть комфортнее печатного по размеру.

---

# 13. Ширина содержимого

Канонический отчёт использует рабочую ширину около `880px` и боковые поля порядка:

- `42px` на широком экране;
- `22px` на узком экране.

Для длинных аналитических материалов это сильный ориентир.

Рабочее приложение может быть шире для таблиц, доказательств и сравнений, но длинный текстовый столбец не должен растягиваться на весь монитор.

---

# 14. Поверхности, границы, радиусы и тени

Основная модель:

- светло-серый общий фон;
- белые аналитические поверхности;
- вторичные серые поверхности;
- тонкая граница в один пиксель;
- базовый радиус `8px`;
- очень мягкая тень.

Текущий ориентир тени:

`0 10px 28px rgba(23, 50, 77, 0.08)`

Тень отделяет слой, но не создаёт эффект плавающей плитки.

В плотных таблицах предпочтительнее граница, а не тень.

---

# 15. Карточки

Карточка используется только для самостоятельной смысловой единицы.

Допустимые объекты:

- риск;
- прогноз;
- среда;
- руководитель;
- доказательство;
- действие;
- противоречие.

Недопустимо превращать каждый абзац в карточку.

Базовая структура аналитической карточки:

1. служебная метка;
2. главный вывод;
3. статус;
4. основание;
5. ограничение;
6. действие или раскрытие.

---

# 16. Секционная система

Существующий канон использует:

- номер раздела;
- заголовок;
- короткую служебную пометку;
- нижнюю линию;
- содержимое ниже.

Эта система должна переиспользоваться в:

- методологии;
- отчётах;
- длинных исторических кейсах;
- экспертном представлении.

В рабочем приложении номер раздела не обязан присутствовать постоянно, но ясная секционная граница сохраняется.

---

# 17. Визуальный язык данных

Предпочтительные формы:

- таблица;
- полосовая диаграмма;
- сравнительная матрица;
- временная шкала;
- перечень состояний;
- структурная карта;
- две сопоставленные колонки;
- последовательность «основание → механизм → прогноз».

Без специальной необходимости не использовать:

- трёхмерные графики;
- спидометры;
- декоративные круговые диаграммы;
- радиальные шкалы;
- пузырьковые облака;
- псевдонаучные сети связей.

---

# 18. Большое число и шкалы

Канон использует очень крупное число для центрального структурного показателя.

Этот приём допустим только если:

- показатель действительно центральный;
- рядом явно указано его название;
- пользователь понимает его смысл;
- он не воспринимается как вероятность успеха;
- рядом есть объяснение.

Любая шкала должна иметь:

- название показателя;
- крайние значения;
- смысл диапазона;
- текущую отметку.

Если шкала не имеет вероятностного смысла, она не должна выглядеть как вероятность.

---

# 19. Временная шкала

Временная шкала является одной из ключевых визуальных форм MergeVue.

Каноническая структура уже использует:

- фазу;
- временное окно;
- ожидаемое проявление;
- проверяемый признак.

Эта форма должна стать общим компонентом для:

- публичного анализа;
- платного прогноза;
- индивидуального прогноза;
- последующей проверки.

---

# 20. Прогноз как самостоятельный компонент

Канонический отчёт показывает прогноз отдельным блоком, содержащим:

- идентификатор;
- состояние фиксации;
- утверждение;
- срок проверки;
- метаданные.

Будущий продукт должен сохранить эту самостоятельность.

Прогноз нельзя прятать внутри длинного общего текста.

Зафиксированный прогноз должен выглядеть как аудиторская запись, а не как игровое достижение.

---

# 21. Доказательства

Доказательство должно ощущаться как проверяемая запись.

Базовые элементы:

- источник;
- дата;
- класс;
- краткий фрагмент;
- отношение к выводу;
- статус;
- уровень доступа.

Не следует оформлять доказательство как обычный комментарий пользователя.

---

# 22. Противоречия и неизвестность

Противоречие показывается заметно, но без театрализации.

Структура:

- две стороны;
- объект расхождения;
- статус разрешения;
- следующий шаг.

Неизвестность имеет отдельный нейтральный статус.

Она не должна выглядеть как:

- ошибка;
- плохая оценка;
- красный риск.

---

# 23. Риск

Риск должен визуально состоять из:

> название → механизм → значение для сделки → основание → временное окно → действие

а не из:

> красная иконка → «высокий риск».

Это одна из центральных дизайнерских границ MergeVue.

---

# 24. Экономическая экспозиция

Финансовая информация должна выглядеть как часть инвестиционного анализа.

Предпочтительно:

- диапазоны;
- единицы измерения;
- происхождение;
- допущения;
- компактная таблица.

Не использовать:

- драматические красные суммы;
- счётчик «денег под угрозой»;
- анимированные потери;
- псевдоточность.

---

# 25. Девять сред взаимодействия

Страницы сред не должны выглядеть как каталог типов личности.

Не использовать:

- портреты персонажей;
- архетипические изображения людей;
- эмоциональные лица;
- характерологические значки;
- «карточки личности».

Среда описывается визуально через:

- структуру;
- полномочия;
- решения;
- ресурсы;
- поведение системы под давлением;
- взаимодействие с другой средой.

Все девять сред имеют равный визуальный статус.

---

# 26. 42Q

Интерфейс 42Q должен быть самым нейтральным пространством продукта.

Цель:

> минимизировать влияние оформления и контекста сделки на ответы.

Использовать:

- белый или нейтральный фон;
- один вопрос в фокусе;
- понятные варианты;
- спокойный показатель прогресса;
- минимум дополнительной информации.

Не использовать:

- риск сделки;
- название предполагаемой среды;
- предполагаемый тип;
- фотографию руководителя;
- эмоциональную цветовую обратную связь;
- «правильные» и «неправильные» ответы.

---

# 27. Персональный прогноз руководителя

Карточка руководителя может показывать:

- имя;
- должность;
- организацию;
- деловую роль;
- зависимость сделки;
- прогноз;
- наблюдаемые признаки.

Фотография руководителя не является обязательным элементом.

Особенно нельзя автоматически помещать лицо рядом с крупным красным индикатором риска: это способно превратить прогноз поведения в визуальную оценку личности.

---

# 28. Публичный сайт

Публичный сайт должен наследовать аналитический язык продукта.

Использовать:

- много воздуха;
- крупную, но не кричащую типографику;
- сдержанный синий акцент;
- реальные структурные схемы;
- фрагменты настоящих аналитических компонентов;
- минимум декоративной фотографии.

Первый экран не строится вокруг:

- светящейся сферы;
- сетки нейронов;
- фиолетового «ИИ-градиента»;
- изображения рукопожатия;
- абстрактного технологического фона.

---

# 29. Методологическая библиотека

Методология должна иметь редакционный характер:

> профессиональная аналитическая публикация внутри продуктовой системы.

Использовать:

- текст ограниченной ширины;
- локальное содержание;
- секционные номера;
- определения;
- схемы;
- примеры;

- саму временную отсечку;
- прогноз;

Временная граница должна быть визуально очевидной.

# 32. Навигация рабочего пространства

Боковая навигация:

Базовый принцип:

Нельзя уходить в крайности.

## Слишком разреженно

Каждый небольшой факт занимает огромную карточку.

## Слишком плотно

Интерфейс напоминает необработанный реестр.

MergeVue должен одновременно быть понятен старшему руководителю и полезен аналитику.

Таблица является нормальной и важной формой.

Не нужно заменять профессиональную таблицу карточками только ради «современности».

Таблица предпочтительна для:

- доказательств;
- сравнений;
- участников;
- версий;
- статусов;

Стиль:

- тонкие линии;
- белый фон;
- мягкий серый для служебной зоны;
- умеренные отступы;
- чёткая числовая колонка;
- минимум тяжёлых рамок вокруг каждой ячейки.

---

# 35. Кнопки и формы

Основная кнопка использует синий акцент.

Вторичная кнопка использует нейтральную границу.

Красный применяется только к действительно опасному или необратимому действию.

Формы должны иметь:

- явную подпись над полем;
- пояснение при необходимости;
- ошибку рядом с полем;
- вариант «не знаю» там, где он допустим;
- сохранение введённых данных;
- логическую группировку.

---

# 36. Длинные опросы

Не выводить десятки вопросов на одной странице.

Использовать:

- смысловые блоки;
- состояние прогресса;
- сохранение;
- возможность продолжить;
- минимум визуального шума.

При этом нельзя создавать ложное ощущение короткого процесса путём скрытого дробления на неожиданно большое число шагов.

---

# 37. Состояния загрузки, ошибки и ограничения

Аналитическая система может работать дольше обычного интерфейса.

Пользователь должен видеть:

- реальную стадию;
- что уже завершено;
- что выполняется;
- требуется ли его действие.

Состояние «недостаточно оснований для вывода» является отдельным нормальным состоянием, а не ошибкой.

Оно должно выглядеть нейтрально и ясно.

Он не должен конкурировать с главным выводом.

# 39. Отчёт и рабочее пространство

Представление отчёта в браузере должно быть максимально родственным рабочему пространству.

Если в рабочем пространстве существует:

- риск;
- прогноз;
- доказательство;
- временная шкала;
- экономическая экспозиция,

тот же объект в отчёте должен выглядеть узнаваемо.

Отчёт — это утверждённое представление тех же объектов сделки, а не отдельная дизайнерская система.

# 40. Клиентский и экспертный интерфейс

# 44. Градиенты, полупрозрачность, иконки и анимация

Градиент в текущем каноне используется локально, в том числе в знаке бренда.

Он не является основным строительным материалом интерфейса.

Полупрозрачность допустима в служебном навигационном слое, но аналитические карточки не должны становиться «стеклянными».

Иконки применяются только для ускорения распознавания.

Анимация допустима для:

- раскрытия;
- навигации;

Не использовать:

- декоративные «нейронные сети».

- доказательствах;

2. задача действительно новая;

4. существует понятный повторный сценарий его применения;
5. он не создаёт новый визуальный язык.

Не являются автоматическим улучшением:

- скрытие таблиц;
- превращение аналитики в плитки.

Современность MergeVue определяется:

> ясностью, скоростью понимания и качеством аналитической иерархии.
